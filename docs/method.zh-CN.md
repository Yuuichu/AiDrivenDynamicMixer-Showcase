# 方法

这套分析回答一个范围很窄的问题：**在什么地方、程度多大，有东西干扰了可懂度或空间声像？** 它用数字和时间范围来回答，并且从不改动工程。

## 1. 特征提取 —— 参数化的，不是原始音频

每条轨道逐帧分析（默认帧长 250 毫秒），产出：

| 特征 | 说明 |
|---|---|
| **8 频段能量** | `40-80`、`80-160`、`160-320`、`320-640`、`640-1250`、`1.25k-2.5k`、`2.5k-5k`、`5k-10k` Hz |
| **响度** | dBFS 近似值 |
| **L/R 相关性** | 立体声相干性，`+1` = 单声道兼容 |
| **立体声宽度** | Side/mid 关系 |
| **空间可用性** | 该来源是否具备空间信息（单声道轨道被标记为不可用，而不是被评为完美） |

实现说明：

- WAV 读取使用**标准库**；运行分析不需要沉重的音频依赖。
- 滑动窗口频段分析使用 **Goertzel 算法**而不是完整 FFT，因为只需要测量八个频段。
- **numpy 是可选的**——是加速器，不是前提条件。

这一层刻意*不是*什么：不是原始采样或全 STFT 管线。特征数量少、有名字、可复现，这正是报告可以被质疑的原因，也是分析成本能保持低廉的原因。

## 2. 检测判据

### 对白掩蔽

逐帧评估，且仅在**语音清晰度频段**：`1.25k-2.5k` 与 `2.5k-5k`。辅音可懂度就在那里；其他频段的掩蔽是另一个（也没那么紧迫的）问题。

```text
if dialogue_loudness_db > -60                              # dialogue is actually present
   and (masker_clarity_db - dialogue_clarity_db) >= -3.0:  # masker is close to or above dialogue
        issue = dialogue_masking
        severity = min(1.0, max(0.1, (masker_clarity_db - dialogue_clarity_db + 6.0) / 18.0))
```

解读这个严重度公式：3 dB 的差距得到 0.1 的下限，重叠越大越向 1.0 上升，而 `+6 / 18` 这个缩放被选定，是为了让有用区间被完整铺开，而不是立刻就饱和。

`> -60 dBFS` 这个保护条件很重要：没有它，静音也会被报成掩蔽，因为两条极安静的轨道可以永远「相差在 3 dB 以内」。

### 空间冲突

```text
if track_loudness_db > -55.0
   and lr_correlation < -0.2
   and stereo_width  > 0.4:
        issue = spatial_conflict
```

三个条件都必须满足。响度起门控作用（静音的轨道不可能与任何东西冲突），相关性抓住反相素材，宽度抓住宽到无法安放在声像里的素材。

### 对白宽于中央声像

第三项检查，与教科书上的那项不同：

```text
if dialogue is spatially active
   and stereo_width > 0.4:
        issue = dialogue_wider_than_expected
```

一条对白分轨不需要出现负相关就已经是问题了：宽度过大本身就会损害可懂度与定位，因此它被单独报告，而不是并进相关性检查里。

## 3. 建议

检测到的问题由**确定性规则引擎**（`core/ai_reasoning/rule_engine.py`）转换为具体操作——不调用模型、无随机性，同样的输入 → 同样的输出。

每条建议包含：

- **操作**（例如 `dynamic_eq_ducking`），
- **建议量**：频段范围、增益 dB 数、启动与释放时间，
- 一个**置信度**值，
- `requires_human_review: true`，
- 面向 REAPER 与 Wwise 的**宿主映射提示**，每一条都表述为给人复核者的指示。

示例（仅为说明，来自仓库的合成示例分轨）：`music_pad` 在清晰度频段与 `dialogue_main` 重叠，产生一条闪避建议：1250–5000 Hz、−2.5 dB、启动 120 毫秒、释放 700 毫秒，置信度 ≈ 0.35。

低置信度加上强制复核标记就是预期的行为：这个工具的职责是指出某个具体时刻，而不是做决定。

## 4. 这个工具不会做什么

- 它不写自动化、RTPC、快照或工程文件。
- 它不渲染也不修改音频。
- 它不判定混音已经完成。

REAPER 与 Wwise 适配器的存在是为了*读取*分轨、工程数据与遥测。它们的只读性质是设计本身，而不是日后要移除的限制。

## 5. 已知弱点

- **响度是近似值**，不是 BS.1770，因此绝对阈值应被当作启发式规则来读。
- **频段能量没有做感知加权**，因此「3 dB」的差距是一个电平陈述，而不是响度陈述。
- **掩蔽没有做心理声学建模。** 这里没有同时掩蔽曲线；判据是电平与频段的启发式规则，它们被记录下来以便调参。
- **帧分辨率限制时间精度**——发现只能落在帧边界上（默认 250 毫秒）。
- **阈值是在示例素材上调出来的**，应当按类型或按项目重新审视。
